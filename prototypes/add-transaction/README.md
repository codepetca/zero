# Fixed-fixture recoverable Add experiment

This local experiment models **one Add** as review, staged bytes, a durable intent
record, and recoverable roll-forward of the bundle, project POM and pin. It is
not integrated into Zero. Run from the repository root (requires a JDK with `javac` supporting `--release 17`):

```sh
python3 -m unittest discover -s prototypes/add-transaction -p 'test_*.py' -v
```

The fictional accepted record fixes account 11, repository 22, release 33,
coordinate `proof.fixture:fixture:1.0.0`, the exact sizes and SHA-256 hashes in
`add.py`, and an MIT license notice. At test runtime, `fixture_builder.py` generates four files in disposable storage
from the preceding project-owned-bundle proof: a real Java 17 compiled JAR,
source JAR, POM and full license. ZIP metadata is fixed. The expected sizes and
hashes are hardcoded independently in `add.py`, and every test process checks
the generated bytes against them. No generated fixture is retained in Git.
`javac` is required; a compiler producing different class bytes fails closed
rather than silently changing the trusted record. It is a test stand-in, not authenticated catalog/checker evidence.
The POM used for the student project is a deliberately minimal fixed test format,
not a valid production Maven dependency integration. The project pin records all
four hashes. Review fixes prior and proposed hashes, sizes, identity and notice;
apply revalidates the review, fixture and prior bytes. An existing destination,
changed POM or pin, altered notice/review or changed fictional identity blocks.
Cancellation before preparation changes no project file.

## State and recovery

Only the exact fixed prior POM and pin and absent four destination files are
accepted. Preparation creates `.add-transaction/stage`, writes and fsyncs six
proposed files, then atomically publishes a canonical journal and syncs its
parent. After that, each destination must equal its old or proposed bytes;
unknown content blocks before any additional write. Bundle members use no-replace
hard links; the POM and pin are individually replaced after rechecking their old
bytes. The journal and staged bytes are deliberately retained after completion so
repeat recovery can identify the committed result. No automatic cleanup, revert,
update or second transaction is implemented. `.add-lock` is also permanent.

A stop before journal publication leaves the original six project file states
intact but may leave an empty `bundle` directory and an orphan transaction. It
blocks further work and requires manual inspection; the prototype does not infer
that an incomplete or unknown journal is safe to discard. After journal
publication, the project can temporarily contain a mixture of old and new files.
Recovery rolls forward, never claims an unchanged project, and blocks while
preserving unexpected student edits or damaged staged bytes. It can reuse a
verified replacement file left by a crash. A stop after the last replacement but
before the caller receives success is reported as an error by the interrupted
call; recovery verifies all six files and returns `committed`. A detected conflict
is not automatically repaired, and the project may remain mixed until a person
resolves it. The checksum and exact journal schema detect accidental alteration,
not a malicious actor able to rewrite the prototype or its trusted constants.
The interruption hooks run after completed writes, not inside each write or
fsync. A partially written replacement is treated as unknown and blocks for
manual inspection; automatic roll-forward is not established for every possible
interruption.

The experiment assumes a trusted existing project root on one local POSIX
filesystem that supports same-filesystem hard links, atomic rename, advisory
`flock` and directory fsync. All actors that write the six destinations or path
components must cooperate with the permanent lock throughout review/apply or
recovery. The code checks for ordinary pre-existing symlinks but uses pathname
operations and is **not race-safe against an uncooperative or malicious writer**;
no guarantee is made for network filesystems, mount changes, disk hardware,
filesystem bugs, or abrupt power loss. Process termination is tested; directory
fsync calls do not prove power-loss durability. Filesystem permissions and
student edits can block progress. The prototype has no resolution UI.

It does not parse an untrusted archive, validate archive entries, resources,
transitive dependencies, namespace collisions, arbitrary licenses, compatibility,
size policy or redistribution rights. Nor does it authenticate an accepted
record, verify real GitHub or catalog drift, execute Maven/WebFX, test a real
editor buffer, or establish native/browser portability. Real VS Code Add uses
editor edits and save; its POM undo does not roll back a filesystem bundle. A
production design must reconcile dirty buffers, save/undo, review and recovery
explicitly and test the actual UI. This result does not close the ZeroHub plan's
transaction gate or authorize publication.

## Local receipt

On 2026-11-02, source base `f76d931e`, macOS Darwin arm64, Python 3 and Temurin JDK 21.0.12.1, the above
13 focused tests passed without network or external services. They include normal
Add and repeat recovery, cancellation, fictional account/review drift, nested review mutation and failed fixture configuration, existing
file and student-edit conflicts, same-length fixture tamper and missing each
member (including the license), damaged/unknown journal and staged bytes,
symlinks, injected write failure, competing lock attempts in another process,
and a failure after the final installed write. Separate child processes called
`os._exit(71)` after transaction creation, each of six staged writes, journal
publication, each of six installs, and each of two replacement staging writes.
Before the journal the six prior file states remained and recovery blocked; after
publication recovery produced the exact six proposed hashes and repeat recovery
reported committed. No Windows/Linux, real full-disk or locked-file filesystem,
power-loss, VS Code UI, authenticated service, update/revert, or live build was
run. Simulated write errors and process exits do not establish those cases.
